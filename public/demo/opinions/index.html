Atlas — unstructured opinion agent

Overview

When a public company is sold, its board hires an investment bank to answer in writing: "Is the price fair to the shareholders?" The resulting documents, fairness opinions, are among the most litigated documents a bank produces. When a deal is challenged, the questions are always about the record: what exactly did the opinion cover, what did comparable opinions assume, and so on.

Today, consulting the record means someone manually digging through hundreds of filings. Interest in improving this process comes from the top of the firm: senior leadership wants to be able to ask arbitrary questions of these documents, and obtain answers on the spot.

A structured assistant already exists, which is capable of answering questions with column-shaped answers (e.g. counts, breakdowns) from a curated dataset. But the answers to many questions that C-suite might ask live in prose, not columns: what an opinion said, how it was worded, what assumptions comparable deals used. Answering those requires working from the raw filings themselves.

The existing unstructured assistant is a model with the documents stuffed into its context window. This fails for several reasons:

  • It can't see the full corpus: a context window fits only a few dozen opinions out of 583.
  • It has no tools: computations occur inside the model's latent space, which works for simple arithmetic but fails for anything harder.
  • It can't guarantee completeness: "Average over [X]" is computed over whatever was retrieved, which (for the above reasons) is non-deterministic.

The idea behind this unstructured assistant, Atlas, is to replace the single context window with an agent equipped with three simple tools: document-level embeddings for precedents/outliers, chunk-level embeddings for assumptions/wording, and a scan for aggregates, plus a few trivial tools: a metadata counter, a page reader, a calculator. This approach has the advantage of simplicity: each tool is a small deterministic function, and the model underlying the agent is used in its ideal capacity, for judgment.

Architecture

When a question is asked, it is sent to an LLM (henceforth the "agent"). The agent reads the question, picks the appropriate tool to call, inspects the result, and calls further tools if needed. When it has enough evidence, it writes the answer, with a citation attached to each claim.

The most important decision is the first one: which tool to use. A lookup goes to passage search, a precedent question goes to document similarity, a count or average goes to scan. If the agent routes wrong, the answer will be wrong, so the agent's system prompt contains explicit description of each tool and its limitations.

Each opinion is embedded at two levels. Document-level vectors represent each opinion as a whole, and are used for precedent and outlier questions. Chunk-level vectors represent individual passages, and are used to find where something is said, or to locate specific concepts. Embeddings can't answer aggregate questions, because retrieval returns the top matches rather than all of them, so the "scan" tool uses a cheap language model to read every document that passes a metadata filter. The remaining tools (metadata counter, page reader, calculator) exist so the model doesn't count or do arithmetic itself.

I also created an evaluation set consisting of questions with verified answers, including traps (like questions about deals that aren't in the corpus).

Embeddings

The corpus is 583 documents. Questions can be phrased using words the documents never use, so exact-matching is insufficient. This is an ideal use case for embeddings.

An embedding maps text such that the distance between semantically similar pieces of text is minimized. In this case, embeddings are useful because fairness opinions are templated; what matters is which family an opinion belongs to and where it deviates, which are both naturally geometric questions.

Document level — "which opinions are like this one?"

This is the higher-level embedding: naively, we embed each opinion as a vector. This is useful for precedent search, and a general sanity check; a deal's letter, description, and supplement should be close to each other across volumes (they are).

My initial approach, which was a failure: simply embed each document's raw text in one call. This failed because the shared boilerplate language dominates the average (coarseness problem) so everything resembles everything, and artifacts/confounds leak in.

The perfected approach blends two channels. The first, stated simply, is: strip the header (as it appears in each opinion); count every word and word-pair; down-weight terms that appear in every opinion (i.e. "fairness," "Evercore") and up-weight terms that don't ("EBITDAX," "exchange ratio"); then compress the counts down to a short vector. Two opinions are similar when their arrows point the same way.

The second channel is neural embeddings, which had to be corrected before they were usable: the raw neural vectors did worse than the word counts (below chance on one family), because every vector is ~84% the same direction — "this is a fairness opinion." Subtracting that shared direction, and the top two components after it, fixed the channel. The blend of the two beats either alone: precision 0.67, vs 0.65 neural-only and 0.55 counts-only, measured over 143 queries.

A simple piece of evidence that this pipeline works: the 8point3 deal's nearest neighbors are the MLP conflicts-committee precedent set [Blueknight (.59), DCP Midstream (.59), PetroLogistics (.56), TransMontaigne (.55)] which is what we should expect.

Chunk level — "where does it say that?"

This is the lower-level embedding: each passage is embedded as a vector. There are 9,588 vectors total (8,521 text passages and 1,067 tables). This is the layer the agent directly reads from. I attached the metadata to each vector [every hit carries (deal, document, page)] so citations are very native and natural for the model to give.

Initial approach, naive failures: using doc vectors for specific questions (i.e., the terminal-value paragraph is only ~0.3% of its full document, so using document-level vectors matches "is this a pharma opinion," not the paragraph in question) and fixed-width chunking (which leads to cut/orphans mid-sentence/mid-table.)

The corrected method: cut each document into pieces of about a page, breaking only at paragraph or sentence ends; tag each piece with its deal, document, and page; keep tables as their own pieces; prepend each piece's section heading so a table of numbers still knows it belongs to the DCF. Embed every piece; embed the question the same way. Then, return the pieces whose arrows point most nearly the same direction, each with deal, document, page.

The embeddings power two of the agent's tools: find_similar (precedents and outliers) and search_passages (passage retrieval with citations).

Scan

Embeddings work well for [X], but some questions are aggregates: "what is the average discount rate across our healthcare deals from the past two years." In this case, the answer does not exist in any single document, but is computed across many. Retrieval is not the right tool in this case. If one relevant document is not retrieved, the average is wrong, and there's essentially no way to tell. The only way to guarantee an aggregate is to read every document that could matter, which is why the scan tool exists.

The scan procedure works as follows: filter the corpus by metadata (year, document type, deal, adviser) to get a universe of documents. Then, for every document in the universe, either count a pattern (for simple questions), or have a small, cheap model read the document and pull out one value (about $0.01 per document). The extracted values go into code for the arithmetic (min, max, mean).

There are two modes. Pattern mode, e.g. "how many opinion letters are addressed to a conflicts committee", is answered by searching the opening block of all 282 letters for the phrase (34 of them are). Extract mode is for values that are more nuanced, and need reading: i.e. for the question "Discount rate", the reader model goes through each recent description, returns the rate or "not stated," and the statistics are computed over the returned rows.

An early failure, which I think is worth describing: the corpus metadata has no sector field, and inferring sector from company names does not work. On an early run, picking the healthcare deals by name missed Augmedix (a 2024 healthcare deal with a name that doesn't sound like one). The fix I decided on is to filter loosely and let the reader model decide relevance for each document. An over-included document costs less than a cent, and the agent can easily ignore it.

The agent

The orchestrator is claude-opus-4-8 with six tools and hard rules. The design principle, inherited from the structured assistant: definitions live in tools, where they are pinned and testable — the model routes, reads, and synthesizes with citations, and never invents a corpus fact.

ToolAnswersGuarantee
list_documentshow many, which deals, breakdowns by adviser / year / kindexact counts over the manifest; free
search_passages"where does a document discuss X"best-matching passages with page citations; never used to count
read_documentthe exact wording of specific pagesverbatim filing text
find_similarprecedents ("opinions like X") and outliersa ranking over every document in the volume
scan_documentscount or extract something from every matching documentcompleteness by construction; regex free, reader ~$0.01/doc
calcarithmetic over tool outputsdeterministic; the model never does mental math

The rules that do the most work:

  • Counts never come from search — top-k retrieval is not exhaustive, so anything shaped like "how many" or "all deals that…" must go through the manifest or a scan.
  • Every factual claim carries a citation, [Target ~ Acquirer, doc-kind, p.N], checkable against the filing in seconds.
  • Every count states its operationalization: which field, which pattern, which universe.
  • Scope precision: what an opinion expressly does not address is reported as carefully as what it does — a fairness conclusion is never extended to parties the letter excludes.
  • Abstention is scoped: if the corpus can't support part of an answer, the agent names the missing piece and answers the rest. Asked about a deal that isn't in the corpus, it says so rather than summarizing from memory.

Evaluated on a 12-question set spanning single-document lookups, metadata aggregates, text-scan counts, precedent retrieval, and two traps (a scope trap and an absent-document trap): 12/12 — including one case where the agent corrected the answer key, finding a growth-rate disclosure under a terminology variant the key's detector had missed, with the correct attribution. The honest caveat: the eval was authored alongside the system; the next round of questions should come from its users.

Cost per question: metadata and lookups $0.04–0.07, outlier explanations ~$0.15, a full reader scan ~$0.40.
